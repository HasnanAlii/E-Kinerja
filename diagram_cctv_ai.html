Diagram Sistem Pengawasan Pegawai (CCTV AI)

E-Kinerja — Logika & Perhitungan Monitoring Kehadiran

Diagram 1: Arsitektur Sistem (Overview)

graph TD A["👤 Atasan\n(Browser)"] -->|"Kirim frame\nsetiap 500ms"| B["POST /api/process-frame\n(Flask Python)"] A -->|"Polling setiap 5s"| C["GET /api/stats\n/api/log-deteksi"] B --> D["🤖 YOLOv8n\n(Deteksi Person)"] D --> E["Zone Matching\n(Point-in-Rectangle)"] E --> F[("MySQL\ncctv_monitoring_logs\ndeteksi_aktivitas\nzona_kameras")] C --> F F -->|"JSON response"| A G["👤 Pegawai"] -->|"Absen manual\n(check_in)"| H["POST kehadiran\n(Laravel)"] H --> I[("MySQL\nkehadirans")] I -->|"total_hadir"| C
Keterangan:
Diagram ini menggambarkan alur data keseluruhan sistem E-Kinerja.
Terdapat dua jalur data yang terpisah:

  • Jalur CCTV (kiri): Browser Atasan mengirimkan frame kamera setiap 500ms ke layanan Python Flask. Frame diproses oleh YOLOv8 untuk mendeteksi keberadaan pegawai di zona meja mereka. Hasil deteksi disimpan ke tiga tabel MySQL yang dikelola Python (cctv_monitoring_logs, deteksi_aktivitas, zona_kameras).
  • Jalur Absensi Resmi (kanan): Pegawai melakukan absen masuk secara manual melalui Laravel, yang mencatat data ke tabel kehadirans. Data ini menjadi sumber "Total Pegawai Hadir" di dashboard.

Kedua jalur tidak saling menulis satu sama lain — kamera tidak mengubah data absensi resmi, dan absensi resmi tidak mempengaruhi log CCTV.

Diagram 2: Sistem Koordinat Zona (Percentage-Based)

graph LR subgraph Frame["📷 Frame Kamera (640 x 480 px)"] direction TB TL["(0%, 0%)"] --- TR["(100%, 0%)"] TL --- BL["(0%, 100%)"] TR --- BR["(100%, 100%)"] subgraph ZonaA["Zona Meja A\nx1=10% y1=5%\nx2=45% y2=90%"] PA["👤 Pegawai A"] end subgraph ZonaB["Zona Meja B\nx1=55% y1=5%\nx2=90% y2=90%"] PB["👤 Pegawai B"] end end subgraph Rumus["Konversi ke Piksel"] R1["x1_px = x1_pct / 100 × W"] R2["y1_px = y1_pct / 100 × H"] R3["x2_px = x2_pct / 100 × W"] R4["y2_px = y2_pct / 100 × H"] end
Keterangan:
Diagram ini menjelaskan bagaimana posisi zona meja pegawai disimpan dan direpresentasikan dalam sistem.

Zona tidak disimpan dalam piksel absolut, melainkan dalam persentase terhadap lebar (W) dan tinggi (H) frame kamera (0–100%). Keunggulannya:
  • Zona tetap akurat meskipun resolusi kamera atau ukuran tampilan berubah.
  • Zona yang digambar pada monitor 1920px akan tetap valid jika diputar pada kamera 640px.

Contoh konversi untuk frame 640×480:
- x1_pct=10 → x1_px = 10/100 × 640 = 64px
- y2_pct=90 → y2_px = 90/100 × 480 = 432px

Diagram 3: Pipeline Pemrosesan Frame (Per 500ms)

flowchart TD A(["▶ Frame diterima dari browser\n(base64 JPEG)"]) --> B["Decode base64\n→ numpy array → OpenCV"] B --> C{"simulate\n= true?"} C -->|Ya| D["Mode Simulasi\n(tanpa kamera nyata)"] C -->|Tidak| E["🤖 YOLOv8n\nmodel.track(frame, classes=0)"] E --> F["Loop setiap\nbounding box"] F --> G["Hitung titik tengah:\ncx = (x1+x2)/2\ncy = (y1+y2)/2"] G --> H["Konversi ke %:\ncx_pct = cx/W × 100\ncy_pct = cy/H × 100"] H --> I{"Cocok dengan\nzona mana?"} I -->|"Cocok"| J["Tandai pegawai_id\nsebagai HADIR"] I -->|"Tidak cocok"| K["Orang asing\n(tidak dipantau)"] J --> L["Simpan DeteksiAktivitas\n+ Update CctvMonitoringLog"] D --> L L --> M["db.commit()"] M --> N(["◀ Return: annotated frame\n+ detected_count"])
Keterangan:
Diagram ini menggambarkan seluruh proses yang terjadi setiap kali frontend mengirimkan satu frame kamera (setiap 500ms) ke endpoint POST /api/process-frame.

Langkah-langkah utama:
  1. Decode — Frame diterima dalam format base64 JPEG dan dikonversi ke format matriks citra OpenCV.
  2. Pemilihan mode — Jika simulate=true (kamera tidak tersedia), langsung ke mode simulasi. Jika tidak, frame diproses oleh YOLOv8.
  3. Deteksi & tracking — YOLOv8 mendeteksi semua objek kelas "person" (manusia) di frame dan memberikan bounding box beserta tracking ID unik.
  4. Pencocokan zona — Untuk setiap objek terdeteksi, titik tengahnya dicocokkan dengan zona yang terdaftar.
  5. Penyimpanan — Hasil cocok disimpan ke database; orang yang tidak cocok zona diabaikan.
  6. Return — Frame yang sudah dianotasi (dengan kotak deteksi & label) dikirimkan kembali ke browser.

Diagram 4: Algoritma Pencocokan Zona (Zone Matching)

flowchart TD A(["cx_pct, cy_pct\n(titik tengah objek)"]) --> B["Ambil semua zona\ndari zona_kameras"] B --> C["Periksa zona ke-i"] C --> D{"zona.x1_pct ≤ cx_pct\n≤ zona.x2_pct\nDAN\nzona.y1_pct ≤ cy_pct\n≤ zona.y2_pct"} D -->|"✅ Cocok"| E["Return zona ini\n(first-match)"] D -->|"❌ Tidak cocok"| F{"Masih ada\nzona berikutnya?"} F -->|"Ya"| C F -->|"Tidak"| G["Return None\n(orang asing / tidak dikenali)"]
Keterangan:
Diagram ini menjelaskan cara sistem menentukan apakah seseorang yang terdeteksi di frame berada di zona meja milik pegawai tertentu.

Algoritma yang digunakan adalah Point-in-Rectangle: sistem memeriksa apakah titik tengah (center point) dari bounding box orang yang terdeteksi jatuh di dalam persegi panjang zona yang sudah dikonfigurasi.

  • Jika cocok: Orang tersebut diidentifikasi sebagai pegawai pemilik zona, dan statusnya dicatat sebagai di_meja.
  • Jika tidak cocok dengan zona manapun: Orang tersebut dianggap "tidak dikenal" — hanya ditampilkan di frame tapi tidak disimpan ke database.
  • Jika dua zona tumpang tindih: Zona yang lebih dulu ditemukan di database yang diprioritaskan (first-match).

Diagram 5: Perhitungan Durasi di Meja

flowchart TD A(["Pegawai terdeteksi\ndi zona (present=True)"]) --> B{"Record hari ini\nsudah ada di DB?"} B -->|"Belum"| C["Buat record baru:\nwaktu_mulai = now\ndurasi_stay = 0\nstatus = di_meja\nlast_seen = now"] B -->|"Sudah ada"| D["Hitung jeda:\ntd = now − last_seen"] D --> E{"td < 60\ndetik?"} E -->|"✅ Ya\n(sesi aktif)"| F["Hitung total sejak awal:\ntotal_secs =\nnow − waktu_mulai"] F --> G["durasi_stay =\nmax(durasi_sekarang, total_secs)"] G --> H["Update:\nstatus = di_meja\nlast_seen = now\nwaktu_selesai = now"] E -->|"❌ Tidak\n(jeda terlalu lama)"| H C --> I(["Simpan ke DB"]) H --> I subgraph Rumus["📐 Rumus Inti (Drift-Free)"] R["durasi_stay =\nmax(durasi_stay_lama,\n(now − waktu_mulai).total_seconds())"] end
Keterangan:
Diagram ini menunjukkan bagaimana sistem menghitung dan menyimpan durasi pegawai berada di meja kerjanya.

Metode yang digunakan adalah Session-Based, Drift-Free:
  • Durasi dihitung dari waktu_mulai (pertama kali terdeteksi hari ini) hingga now, bukan dengan menjumlahkan per-frame.
  • Fungsi max() memastikan durasi tidak pernah berkurang (misalnya jika ada oklusi sesaat).
  • Kondisi td < 60 detik mencegah "lompatan durasi" saat kamera terputus lama lalu tersambung kembali — jika jeda > 60 detik, durasi tidak diperbarui untuk sesi itu.

Hasilnya adalah nilai durasi_stay dalam satuan detik yang akurat dan bebas drift.

Diagram 6: Live Ticking di Frontend (Client-Side)

flowchart TD A(["API response diterima\n(setiap 5 detik)"]) --> B["Simpan ke durationMap:\nbase = durasi_stay_seconds\nbaseTime = now()\nstatus = status_raw"] B --> C["Timer tick\nsetiap 1 detik"] C --> D{"status\n== 'di_meja'?"} D -->|"✅ Ya\n(aktif)"| E["elapsed = now() − baseTime\ntotal = base + elapsed"] D -->|"❌ Tidak\n(keluar/belum)"| F["total = base\n(DIBEKUKAN, tidak bertambah)"] E --> G["Tampilkan:\n≥3600s → 'X Jam Y Menit'\n≥60s → 'Y Menit'\n>0s → '< 1 Menit'\n=0s → '—'"] F --> G subgraph Drift["🔄 Koreksi Drift (setiap kali data API masuk)"] K["myEstimate = base + (now − baseTime)"] K --> L{"|apiValue − myEstimate|\n> 5 detik?"} L -->|"Ya → re-anchor"| M["base = apiValue\nbaseTime = now()"] L -->|"Tidak"| N["Lanjutkan ticking"] end
Keterangan:
Diagram ini menjelaskan mekanisme tampilan durasi yang bergerak secara real-time di antarmuka frontend tanpa harus memanggil API setiap detik.

Prinsip kerja:
  • Setiap 5 detik, frontend meminta data terbaru dari server (durasi_stay_seconds).
  • Data disimpan sebagai base + baseTime (waktu data diterima).
  • Setiap 1 detik, tampilan dihitung dari: total = base + (now − baseTime).
  • Jika pegawai tidak di meja, penghitung dibekukan — durasi tidak bertambah.
Koreksi Drift:
Jika estimasi frontend menyimpang > 5 detik dari nilai server, dilakukan re-anchor untuk menjaga akurasi tampilan selaras dengan data aktual database.

Diagram 7: Transisi Status Pegawai

Keterangan:
Diagram ini menggambarkan semua kemungkinan status pegawai dalam sistem CCTV dan kondisi yang memicu perpindahan status.

Tiga status yang tersedia:
  • belum_terdeteksi: Pegawai belum pernah terlihat di zona hari ini, atau belum memiliki zona yang dikonfigurasi
  • di_meja: Pegawai aktif terdeteksi berada di zona meja kerjanya
  • keluar_ruangan: Pegawai tidak terdeteksi lebih dari 10 detik — dianggap meninggalkan area
Toleransi 10 detik sengaja dirancang untuk menghindari perubahan status yang terlalu sensitif (misalnya saat badan pegawai tertutup sebentar oleh objek lain / oklusi).

Diagram 8: Perhitungan Statistik Dashboard

flowchart LR subgraph DB["🗄️ Sumber Data"] K["Tabel: kehadirans\n(absen resmi Laravel)"] CL["Tabel: cctv_monitoring_logs\n(log CCTV hari ini)"] end subgraph Stats["📊 Kartu Statistik Dashboard"] S1["🔵 Total Pegawai Hadir\n─────────────────\nCOUNT(*)\nFROM kehadirans\nWHERE jenis = 'hadir'\nAND tanggal = hari_ini"] S2["🟠 Terdeteksi Keluar\n─────────────────\nCOUNT(*)\nFROM cctv_monitoring_logs\nWHERE status_terakhir\n= 'keluar_ruangan'\nAND tanggal = hari_ini"] S3["🟢 Rata-rata Stay\n─────────────────\nUntuk setiap log:\n dur = durasi_stay\n Jika di_meja & elapsed < 60s:\n dur += elapsed\nAvg = Σdur / N"] end K --> S1 CL --> S2 CL --> S3
Keterangan:
Diagram ini menjelaskan dari mana setiap angka di tiga kartu statistik dashboard diambil dan bagaimana dihitung.

  • Total Pegawai Hadir (Biru): Bersumber dari tabel kehadirans Laravel — hanya pegawai yang telah melakukan absen masuk resmi (jenis='hadir') yang dihitung. Tidak terpengaruh oleh deteksi kamera.
  • Terdeteksi Keluar Ruangan (Oranye): Bersumber dari log CCTV — menghitung berapa pegawai yang saat ini berstatus keluar_ruangan hari ini.
  • Rata-rata Stay di Meja (Hijau): Menggunakan koreksi live — untuk pegawai yang masih berstatus di_meja dan baru saja terdeteksi (< 60 detik lalu), sistem menambahkan waktu yang telah berlalu sejak last_seen ke durasi_stay sebelum dirata-rata. Ini membuat nilai rata-rata konsisten dengan tampilan durasi di tabel pegawai.

Diagram 9: Mode Simulasi — Rotasi Slot Absen

flowchart TD A(["simulate = true\n(kamera tidak tersedia)"]) --> B["Ambil semua zona\n(N zona terkonfigurasi)"] B --> C{"N > 1\nzona?"} C -->|"Ya"| D["Hitung slot absen:\nabsent_slot =\nfloor(detik_sekarang / 8) mod N"] C -->|"Tidak (N=1)"| E["absent_slot = -1\n(selalu hadir)"] D --> F["Loop setiap zona ke-i"] E --> F F --> G{"i == absent_slot?"} G -->|"Ya → ABSEN"| H["present = False\nGambar tanda 'keluar'\nconfidence = 0.0"] G -->|"Tidak → HADIR"| I["present = True\nGambar siluet pegawai\nconfidence = 0.99"] H --> J["_update_monitoring(present=False)"] I --> J J --> K{"Zona\nberikutnya?"} K -->|"Ya"| F K -->|"Tidak"| L(["db.commit()\nReturn annotated frame"]) subgraph Contoh["📌 Contoh: 3 Zona, detik = 20"] EX["absent_slot = floor(20/8) mod 3\n= 2 mod 3 = 2\n→ Zona ke-3 dianggap absen"] end
Keterangan:
Diagram ini menjelaskan bagaimana sistem berperilaku ketika tidak ada kamera nyata yang tersedia (mode simulasi).

Tujuan mode simulasi:
Memungkinkan Atasan melihat tampilan dashboard yang hidup dan dinamis untuk keperluan demo atau pengujian sistem tanpa harus menyiapkan kamera dan pencahayaan.

Mekanisme rotasi:
Setiap 8 detik, satu zona secara bergilir dianggap "kosong/absen". Rumus floor(detik / 8) mod N memastikan rotasi terjadi secara merata dan dapat diprediksi.
Detik ke- floor(detik/8) mod 3 Slot absen
0–7 0 0 Zona 1
8–15 1 1 Zona 2
16–23 2 2 Zona 3
24–31 3 0 Zona 1 (ulang)

Keterangan:
Diagram ini menggambarkan interaksi lengkap antara Atasan, antarmuka frontend (Alpine.js), layanan Python Flask, dan database MySQL saat mengkonfigurasi zona meja pegawai.

Alur utama:
  1. Memuat data — Saat modal dibuka, sistem mengambil daftar semua pegawai dan zona yang sudah ada.
  2. Pemilihan pegawai — Atasan memilih pegawai mana yang zonanya ingin diatur atau diubah.
  3. Menggambar zona — Atasan menyeret kursor di atas kanvas yang merepresentasikan area kamera. Koordinat dihitung secara real-time dalam persentase.
  4. Penyimpanan — Data dikirim ke API. Jika pegawai sudah memiliki zona sebelumnya, zona lama akan di-update (bukan duplikasi). Jika belum ada, zona baru dibuat.
  5. Konfirmasi — Kanvas diperbarui otomatis untuk menampilkan semua zona terkini.
